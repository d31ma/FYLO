Encryption & access

Two separate mechanisms, deliberately not merged: field-level encryption for confidentiality and application identities on protected .vdbx databases for authorization. Each is opt-in, and each is honest about what it does not protect against.

Field encryption

Fields listed in a schema's $encrypted array are stored with AES-GCM. Equality queries still work through HMAC blind indexes, so a lookup never has to decrypt. 

{schemaCode}

Nested fields use a slash-separated path (payload/verifier), matching the index field-path format. A dotted path such as payload.verifier is accepted as a literal field name, matches nothing, and silently leaves the field unencrypted — if a field is not being encrypted, check the stored document first.

  • The secret referenced by fylo.encryption.key must contain at least 32 UTF-8 bytes.
  • Configure fylo.cipher.salt with the key; its nonempty secret derives the blind index.
  • Both settings must use explicit secret references; literal credentials in JSON are rejected.
  • The cipher is process-global: one key for all collections.

Decryption is schema-driven and does not depend on write history. A read-only process loads a collection's $encrypted registration on its first read, so replicas, reporting jobs, and event-sourced replay decrypt correctly without writing first.

Reads fail closed. If a field the schema declares $encrypted cannot be decrypted — missing key, wrong key, a value that fails authentication, or a value stored before the field was encrypted — the operation fails with EDECRYPTFAILED naming the collection and field. FYLO never hands back a stored value as if it were plaintext when it cannot verify it.

The consequence: adding a field to $encrypted requires rewriting the documents that already hold a plaintext value for it.

Blind indexes leak frequency. An attacker with index access can count how often a value repeats without decrypting anything — that is the price of indexed equality on encrypted data, and it is a real one for low-cardinality fields.

Application identities

An application identity is a P-256 key pair. Its private key stays in a key store, and a process names it with a key reference such as file:app.pem or keychain:com.example.app. A protected .vdbx database is created by an admin identity, and that admin becomes the database's trust anchor. 

{identityCode}

The admin grants other identities read, write, or admin on the whole database or on one collection. Each grant is a new policy version, signed by the admin. Reads use per-collection keys wrapped for each granted identity, and every write is signed by the identity that made it. 

{grantCode}

A process opens the database as one identity, with --identity, FYLO_IDENTITY, or fylo.identity, and pins the admin with --trust-anchor, FYLO_TRUST_ANCHOR, or fylo.trustAnchor. Binary-backed shims pass these settings to the fylo process they start: 

{configCode}

FYLO does not authenticate end users. Your application checks who the user is; FYLO checks what the application identity may do. An open without an identity fails with ENOIDENTITY, and an operation the identity has no grant for fails with EACCES.
