Buckets & raw files

A bucket stores bytes instead of records. It is the same engine and the same index as a document collection — only the value type differs. What you gain is a queryable, checksummed object store that lives in a plain directory.

Creating and reading

Create the collection with kind file, then store a file by its local path or a URL. FYLO copies the bytes in and keeps no link to the source.

Buckets need the native fylo binary. The browser loader and the iOS, Android, and Flutter clients do not support them in this release and reject kind: 'file' with an error.

The example uses the Node shim, which has a dedicated putFile. Every other shim stores a file by sending the same putData request, with a file field, through its raw request method, and reads it with getFileData the same way — see Language clients. 

{basicCode}

getDoc answers a bucket with the manifest and no bytes. getFileData returns the content — base64 inline, or written to an absolute path when it exceeds one response frame. The layout below is internal and versioned: read through the operation, not the path.

FYLO stores the bytes unchanged:

{pathCode}

The metadata it derives — name, key, extension, contentType, contentLength, etag, checksumSHA256, createdAt, and lastModified — goes through the normal prefix index, so all of it is queryable with findDocs.

Databases written by older FYLO versions, where file collections lived under .collections/, migrate to .buckets/ automatically the first time the engine opens them.

Logical keys

A key is object-style logical metadata, not a filesystem path — the bytes still live under the TTID filename. Keys always begin with /, may be at most 1024 UTF-8 bytes, and cannot contain backslashes, control characters, or . / .. segments. 

{keysCode}

Without a key, a file gets / followed by its source file name; a supplied key is stored exactly as given. FYLO does not make keys unique, so pick unique keys in your application when you need them. To change a key, store the file again under the new key and delete the old record. The key is stored as a user.fylo.key extended attribute on the file, so it moves with the bytes.

Checksums and the integrity audit

Checksums are cached in a user.fylo.checksum xattr stamped with the file's size and mtime, so listings and reads never re-hash contents. The hash is recomputed automatically whenever the stamp stops matching.

The cache trusts its stamp — which means silent corruption that preserves both size and mtime is invisible to the fast path. verifyCollection is the stamp-ignoring audit that closes the gap. It re-hashes the full contents of every file, active and soft-deleted, freshens matching stamps, and reports mismatches without touching the corrupt file's original claim. 

{verifyCode}

The audit reads every byte, so it is slow by design — run it as a scheduled job, never per request. The CLI equivalent exits non-zero when corruption is found, so a cron line is a complete weekly audit: 

{cronCode}

Developer metadata is indexed

Pass developer metadata as the meta argument of putFile, bulk-edit it with setMeta (null removes an entry), and read it with getMeta. 

{metaCode}

On buckets, metadata is indexed under meta/, so it can be queried — including numerically.

{metaQueryCode}

Metadata survives soft delete, restore, and version-control restore. A file's key and metadata live only in its xattrs, so copy a store only with a tool that preserves extended attributes; a raw file whose xattrs were stripped cannot be indexed again from its bytes alone, so restore it from version control or a backup instead.
