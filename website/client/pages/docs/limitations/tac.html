Limitations

What FYLO does not do, stated plainly. Most of these are consequences of the filesystem-first design rather than gaps waiting to be filled — knowing them early is cheaper than discovering them in production.

Limitation Detail
Filesystem-first engine One engine writes to a local path. Remote object storage is not a query, transaction, or built-in backup backend.
Local-filesystem locking PID-aware lock files plus kernel-owned takeover claims; live owners are never evicted by TTL. Use local POSIX filesystems or NTFS, not network or sync filesystems lacking equivalent atomic semantics.
Indexes are derived External writes to data files will not update indexes. Run rebuild() afterwards.
Frequency leaks on encryption HMAC blind indexes for equality reveal value repetition even without decryption.
Process-global cipher One key per process for all $encrypted fields. No per-collection key rotation is built in.
No cross-collection transactions SQL mutations and ordinary writes are atomic within one collection; there is no atomic multi-collection commit.
Timestamp metadata createdAt comes from the TTID; updatedAt comes from file modification metadata.
Bulk import for trusted sources The SSRF guard blocks private addresses and caps at 50 MiB. It is not safe for user-provided URLs.
No arrays of objects A document may hold scalars, nested objects, and arrays of scalars — never an array of objects, at any depth.

Remote access is opt-in and unencrypted

By default every client owns its database directly: the CLI and language shims drive the binary against a local root, and the browser and mobile clients embed the engine over an on-device store.

To reach a root from another machine, run fylo serve next to its disk. It owns the root, requires a shared token, and runs one request at a time. It has no TLS yet, so keep it on loopback, a trusted network, or a tunnel. Mounting a live root over a network filesystem instead inherits that layer's weaker locking and consistency; the supported storage targets are local POSIX filesystems and NTFS.

Where the guarantees hold

Crash recovery is release-gated on local macOS and Linux filesystems and on native x64 Windows over NTFS. POSTIX access control requires a POSIX host — it is not a Windows authorization boundary, and browser, Explorer, and WebView clients cannot enforce it at all. The exclusive root lease is a kernel lock and is unsupported on network, clustered, and object-backed filesystems.
