Native shims stay thin

Native clients spawn fylo exec --loop, negotiate capabilities with a handshake, and map stable error codes into language-native exceptions. Copy the version-matched client file from the release archive; there is no package registry or linked storage implementation to keep in sync.

See Machine protocol for framing and pagination, or Browser & Explorer for the local OPFS and File System Access adapters.

Choose configuration for each FYLO child

Every binary-backed SDK shim accepts an optional config path to an application.json. The native CLI reads the file without changing the host environment. The former env file/map option is replaced by this setting.

The same file can be used by every native shim:

{
    "fylo": {
        "schema": "./schemas",
        "strict": true,
        "shard": { "width": 2 },
        "encryption": { "key": "${FYLO_ENCRYPTION_KEY}" },
        "cipher": { "salt": "${FYLO_CIPHER_SALT}" }
    }
}

Without a config path, the CLI discovers application.json in its working directory. An absent default file uses defaults; an explicitly selected missing file, invalid setting, or unresolved secret reference fails initialization. The same setting is available in the Node/TypeScript, Python, Ruby, PHP, Go, Rust, Java, C#, and Dart shims. Browser and mobile clients configure their storage adapters directly because they do not launch a FYLO child process.

Paths inside JSON resolve from the configuration directory. Keep only secrets in the adjacent .env and explicitly reference them using whole-value ${NAME} strings. Injected environment secrets win over that file; unreferenced variables do not configure FYLO.

Treat configuration and binary paths as trusted bootstrap input, never request or tenant data. Keep secret files private and out of source control. Browser and mobile clients do not load these files implicitly; never publish native secrets in website JSON. See Native configuration for migration and resolution details.
