FYLO, end to end.

FYLO is a document store that ships as one self-contained binary. Documents are plain JSON files on disk; indexes are zero-payload keys that accelerate queries without duplicating data. There is no server and no network protocol — like SQLite, your app opens the database files directly. This page takes you from an empty machine to a first query; everything else is linked below.

1. Install the binary

FYLO is distributed through GitHub Releases, not a package registry. The installer detects your OS and architecture, verifies the release checksum, and puts fylo on your PATH. 

{installCode}

Set FYLO_VERIFY_PROVENANCE=1 before running the installer to also require signed GitHub artifact provenance. It fails closed before installing and needs an authenticated GitHub CLI. Per-platform archives and checksums are on the download page.

2. Choose your configuration

Native FYLO discovers application.json in the working directory. Put settings under the fylo key; paths inside the file resolve relative to its directory. This minimal setup does not require secrets or a schema. 

{
  "fylo": {
    "root": "./data",
    "shard": { "width": 1 }
  }
}

Select a different file with --config or the native client's optional config path. Explicit constructor roots override the JSON root. Keep .env for secrets only and reference those secrets from JSON. See Configuration for precedence, encryption, and migration from the old environment settings.

3. Add a client to your project

Your application never links a library — it spawns the binary and talks JSON to it. Each client is a single dependency-free file you copy in from the version-matched fylo-clients.tar.gz attached to the release. It owns the subprocess, the framing, and typed errors; it never owns a storage decision.

Thirteen clients ship today: Python, Ruby, Node/TypeScript, PHP, Go, Rust, C#, Java, and Dart drive the binary, while the browser, iOS, Android, and Flutter clients embed the engine on-device. See Language clients for the same call sequence in each one.

4. Ask a question

There is no index to declare and no migration to run before a query. Every field of every document is written into the prefix index as the document lands, so a query narrows by binary search and hydrates only the documents that matched.

Which index each operator uses — and where it falls back to a scan — is spelled out in Querying & SQL.

5. Know what is on disk

Nothing about a FYLO root is opaque. You can read a document with cat, diff a collection in Git, and restore one file from a backup without the engine's help.

Only docs/ and .deleted/ are the source of truth. index/ is derived and can be thrown away at any time — fylo rebuild <collection> reconstructs it from the documents. That single property is what makes the rest of the design possible.

What FYLO is not

Reading this early saves time later. FYLO has no server, so there is nothing to connect to over a network. When the database lives on network storage, run your app server next to the files rather than opening the root from another machine. No remote object store is in the query path. There are no cross-collection transactions: a write or a SQL mutation is atomic within one collection. And a document may not contain an array of objects at any depth — that shape wants to be its own collection.

The full list, with the reasoning behind each one, is on Limitations.
