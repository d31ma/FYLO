Schemas & migrations

Schemas are optional, versioned, and enforced by the chex binary. Old documents are not rewritten when the schema moves forward — they are materialized to the head shape in memory by JSON migration steps you write.

Layout

Schemas live under fylo.schema in application.json, one directory per collection. Any directory there containing a manifest.json is auto-created as a collection when the database opens. 

{layoutCode}
{manifestCode}

Schemas are chex regex schemas — a field name mapped to a pattern the value must match. A trailing ? on a field name makes it optional. 

{schemaCode}

Migrations

A migration is JSON, not code (ADR 0018). migrations/v1-to-v2.json lists the steps that turn a v1 document into a v2 one. Steps run in order on the document with _v removed, then _v is stamped with the target version. FYLO chains the step files along the manifest history, so a v1 document written two years ago is materialized in v3 shape without ever being rewritten on disk. 

{migrationCode}

Each step has exactly one operation key, whose value is the field it works on as a slash-separated path, plus that operation's parameters: 

{stepsCode}

A step whose source field is missing does nothing, except set, template and slugify, which always write their field. A field of the wrong type, such as lower on a number, fails the migration.

FYLO never runs JavaScript from a schema folder: a version step that has only an old upgraders/v1-to-v2.js file fails with an error pointing at ADR 0018. A change the steps cannot express is an application update in two versions: add a version whose schema accepts both shapes, rewrite the documents with patchDocs or SQL UPDATE, then add a version that accepts only the new shape.

Behaviour

  • Documents carry _v, their version label.
  • Every read returns documents in the head shape: getDoc, findDocs, joins, SQL SELECT and the hot set. A document stored below the head is decrypted at the version it was written at and migrated in memory; its stored bytes do not change until something writes it.
  • Queries and SQL UPDATE and DELETE match the migrated document, so a query on a renamed field gives the same answer before and after fylo schema migrate. Until the collection converges, a query on a field a migration writes or renames reads every document instead of the index; other fields keep it.
  • A patch of an old document migrates it first, so the stored document moves to the head shape.
  • Strict writes validate against the head schema with the built-in CHEX validator.
  • A document missing _v is treated as the oldest version. One whose _v the schema does not list fails the read with ESCHEMA.
  • fylo schema inspect <collection> reports the validation mode, the head, how many documents are stored at each version and whether the collection has converged, every document at the head. A converged collection's reads cost one comparison of _v. The writer keeps the count for a registry collection beside its registry and recounts it by scan whenever it is stale.
  • fylo schema migrate <collection> rewrites every document below the head version at the head, validating and encrypting it as a write would. It skips documents without _v unless given --include-unversioned.
  • Mutation and query methods await schema bootstrap internally. If you need it settled before a synchronous probe, await fylo.ready().

No arrays of objects

FYLO schemas do not support arrays of objects — declare each nested object as its own collection. A schema that would accept items as a list of records throws on first read, naming the offending path. Arrays of scalars and nested objects used as fields are fine.

This is the same rule the storage layer enforces at write time with EARRAYOFOBJECTS; the schema layer simply refuses to promise something the data model will reject. See Documents & metadata.

Strict mode

Set fylo.strict to true to validate every document against the head schema before it is written. Without it, schemas still drive migrations and encryption registration but do not gate writes. 

{cliCode}

schema doctor is the readiness check: it reports a manifest that disagrees with the files on disk, a missing migration in the chain, or a schema that the data model cannot accept.

Schemas drive encryption

The $encrypted array in a schema is what tells FYLO which fields to encrypt and, just as importantly, which fields must be decryptable on read. That registration is loaded on first read, so a read-only replica decrypts correctly without ever writing. See Encryption & access.
